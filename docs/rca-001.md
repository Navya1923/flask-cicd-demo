# RCA-001: Service not ready after config change (simulated)

> This is a simulated incident in a personal learning project. No real production systems, logs, or data are involved.

| | |
|---|---|
| **Date** | 2026-10-20 |
| **Service** | flask-cicd-demo (Flask app in Docker) |
| **Duration** | ~3 minutes (17:17 to 17:20) |

## Summary

After deploying the image with `FAIL_MODE=true`, the `/ready` endpoint returned `503 Service Unavailable` and logged repeated ERROR messages. The service was restored by rolling back to a known-good image, identified by its commit SHA tag.

## Impact

Readiness checks failed for about 3 minutes. In a real environment, a load balancer or Kubernetes would have stopped sending traffic to this instance, causing reduced capacity or an outage if no other healthy instance existed.

## Timeline

All times are from the same machine clock, on 2026-10-20.

| Time | Event |
|---|---|
| 17:17 | Deployed the image with `FAIL_MODE=true` (bad configuration) |
| 17:19 | Five requests to `/ready` all returned `503`. First ERROR logged at 17:19:39 |
| 17:19 | Ran `analyze_logs.py` on the container logs and identified the repeated error |
| 17:20 | Rolled back to image tag `e5d2a5b905156b8be7b15e69b5c8b290970f4fc4` |
| 17:20 | `/ready` returned `200`, service recovered |

**Note on the gap between 17:17 and 17:19:** the app only logs the readiness error when `/ready` is called, so no ERROR lines existed until the checks ran. In a real system, periodic probes from a load balancer or orchestrator would have surfaced the failure within seconds, so this gap points to a monitoring weakness.

## Detection

The failure was found through manual readiness checks and confirmed with the log analyzer:

```
# Log Summary
Levels: {'ERROR': 5}
First error: 2026-10-20 17:19:39,962 | Last error: 2026-10-20 17:19:39,992
Top errors:
  5x  Dependency check failed: cache connection refused (host=cache:6379)
```

## Root cause

The application was started with a bad configuration (`FAIL_MODE=true`), which made its dependency check fail with "cache connection refused". The readiness endpoint correctly reported the service as not ready.

## Resolution

1. Removed the failing container.
2. Redeployed the previous known-good image using its immutable commit SHA tag.
3. Verified that `/ready` returned `200`.

Rollback was fast because every build is pushed with both `latest` and its commit SHA.

## What went well

- The readiness endpoint flagged the unhealthy state instead of reporting healthy.
- Structured logs made the analyzer script simple and reliable.
- SHA-tagged images made rollback quick and exact.

## What could be improved

- Detection depended on someone manually calling `/ready`.
- There was no automated rollback for an unhealthy deployment.
- Configuration was not validated before deployment.

## Prevention and action items

| Action | Purpose |
|---|---|
| Add a readiness check to the deploy job and fail the pipeline on non-200 | Catch bad configs at deploy time |
| Validate configuration values in CI before building the image | Stop bad config before it ships |
| Add alerting on repeated readiness failures (Prometheus and Grafana) | Reduce time to detect |
| Roll back automatically to the previous SHA tag when the smoke test fails | Reduce time to recover |
| Use staged or canary rollouts with multiple instances | Limit blast radius |
